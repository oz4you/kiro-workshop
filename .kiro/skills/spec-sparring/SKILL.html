Spec 壁打ちセッション

引数で渡された機能名(なければユーザーに確認)について、壁打ちインタビューで Spec 成果物を作成する。

進行ルール(厳守)

  1. 一度に1問だけ質問する。 複数の質問を並べない
  2. 回答が曖昧・矛盾している場合は、具体例や選択肢を示して深掘りしてから次へ進む
  3. 以下の観点を順に押さえる: - 目的とゴール(何のために、成功の定義) - 利用者・利用シーン - 機能範囲(必須/任意) - 非機能要件(セキュリティ、可用性、性能、コスト上限) - 制約(リージョン、既存資産、閉域要件など) - スコープ外の明示
  4. 全論点が出揃ったら要点を復唱してユーザーの合意を得る
  5. 合意後に成果物を順に作成。各ファイル作成後にレビュー承認を待ってから次へ進む

成果物(.kiro/specs/<機能名>/ に作成)

requirements.md

  • ユーザーストーリー形式の要件
  • 受入条件は EARS 形式: WHEN <条件> THEN システムは <動作> SHALL する
  • スコープ外セクションを必ず含める

design.md

  • アーキテクチャ概要と Mermaid 構成図
  • Terraform リソース構成(ファイル分割案)
  • 設計決定の記録: 検討した代替案と却下理由を表形式で(後で /verify-adr が ADR 化に使う)
  • steering(terraform-standards.md 等)との整合を確認した旨を明記

tasks.md

  • 番号付き実装タスクのチェックリスト(- [ ] 1. ...)
  • 各タスクに: 対応する要件番号(トレーサビリティ)、完了条件、想定成果物
  • GitHub Issue 1件に対応する粒度(30〜90分程度)に分割

注意

  • 技術仕様は推測せず Terraform MCP / AWS Documentation MCP で確認する
  • コスト影響のあるリソースは概算を requirements.md に明記する
